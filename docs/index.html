Deployment guide

Running the payroll platform on your own infrastructure

The database, the console, the back office and the payroll-system connector, on hardware you control. This document is written for the person who has to approve, install and then be accountable for it — not for a demonstration.

Summary for a security review

This section answers, in one place, the questions a security review asks first. Every claim in it is expanded later in the document, and every one of them is checkable on your own machine rather than taken on trust.

QuestionAnswer
Where does payroll data liveOn this server only. No employee, payslip or client record is stored on our infrastructure.
Inbound connectionsNone. No firewall rule, no published port, no public DNS record, no VPN.
Outbound connectionsUp to four destinations over HTTPS, listed in §8. One is required; the rest are features you can decline.
Can the vendor reach this machineNo. There is no tunnel, no remote-support channel and no credential of ours on the server. If you want us to see something, you send it.
Data at restEmployee documents and national identity numbers are encrypted with keys generated on this machine at install time and held only by you.
Data sent to an AI vendorPseudonymized text only, through a single process that cannot be bypassed. Documents are converted to text on this server. Attachments are refused by default.
TelemetryCounts, durations and hashes, checked against an allow-list immediately before sending. Leave the values blank and nothing is sent at all.
PrivilegesApplication containers run as an unprivileged user. The automatic updater requires access to the Docker socket — see §9 before deciding.
DeletionStop the stack and delete its volumes. Nothing of yours remains anywhere else.
SubprocessorsNamed in §8. There are more than one, and a review that only asks about the obvious one is not finished.
02

The network boundary

Ten containers on one machine. The six that hold your data sit on a Docker network declared internal, which means the Docker daemon installs no route from it to anywhere. This is not a firewall rule that can be edited and it is not a policy that code has to remember: a process on that network that tried to reach the internet would fail to resolve the name.

Identifying values are replaced before anything leaves, and restored in the answer.

ContainerHolds payroll dataCan reach the internet
Databaseyesno
Console, Adminyesno
Agent, Scheduleryesno
Gatewayin transit onlyyes — the AI vendors, and nothing else
Telemetrynoyes — the reporting endpoint you configure
Web front endnoyes — only to obtain a public certificate, if you use one
Updaternoyes — the image registry

You can confirm the separation yourself at any time, without our help:

# should fail: the applications have no route out
docker compose exec console node -e "fetch('https://example.com').catch(e=>{console.log('no route:',e.message);process.exit(0)}).then(()=>process.exit(1))"

04

Installation

Step 1 — inspect the machine

This writes nothing. It reports what is missing and stops.

git clone https://github.com/Dekel-finance/payroll-onprem.git
cd payroll-onprem
./install.sh check

It verifies Docker and Compose versions, cores, memory, free disk, that the outbound destinations resolve, and that the ports are free. Anything marked ! must be fixed first.

Step 2 — install

./install.sh install

It asks for the first administrator's email and password, then prints the addresses to open. Running it again is safe: it repairs an incomplete install rather than starting a second one.

The system starts empty, deliberately

No clients, no employees, no payslips. Your records arrive through onboarding and the sync from your payroll system. An installation delivered pre-filled would be rows your staff must identify and delete before they could trust anything on screen, and we are not willing to put you in that position.

Step 3 — record what you now hold

Before going further, complete §5. It is the only step in this document that cannot be undone later.

05

Key material, and what cannot be recovered

The installer generates one file, .env, holding this installation's secrets. Two of the keys in it encrypt data at rest: one seals every employee document, the other is what makes a national identity number readable.

This is irreversible, and it is the design

If .env is lost, the data in the volumes cannot be recovered — not by you, not by us, not by anyone. We hold no copy and no escrow. That is precisely what makes the encryption meaningful: there is no key of ours that could be compelled, stolen or mistakenly used. It also means the backup of this file is your responsibility and nobody else's.

# copy it somewhere that is not this machine, before going further
cp .env /secure/offline/location/payroll-env-$(date +%F)

Never regenerate these two keys

Regenerating NATIONAL_ID_KEYS on an installation that already holds records orphans every identity number and every sealed document already written. The rows survive; their contents become permanently unreadable.

Recommended handling

  • Store it where your organisation stores other root credentials — a password manager with an audit trail, or a sealed offline copy.
  • Do not keep the only copy beside the backups. An archive sitting next to the key that decrypts it is one theft, not two.
  • Record who holds it. An install whose key is known only to someone who has left the firm is an outage waiting for its trigger.
06

TLS and certificate trust

The applications are reached over HTTPS at:

 AddressUsed by
Consolehttps://<server>:4201the payroll office

Plain HTTP is not a supported configuration

The applications mark their session cookie Secure, and browsers discard a Secure cookie that arrived over http://. Over HTTP the login page accepts the password, redirects, and returns the user to the login page — indefinitely, with no error in any log. If you are diagnosing a login loop, check the scheme first.

On a private network

The certificate is issued by a small certificate authority running inside your own installation. A public authority cannot issue for a name that does not resolve on the internet — it has to reach the server from outside, which is exactly what this deployment avoids. Export the root certificate once:

docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt .

Then distribute it as a trusted root:

  • Windows — Group Policy: Computer Configuration → Windows Settings → Security Settings → Public Key Policies → Trusted Root Certification Authorities → Import. This is the supported path for a fleet; per-machine double-click works for a pilot.
  • macOS — Keychain Access → System → set to Always Trust, or push via MDM.
  • Linux — copy to /usr/local/share/ca-certificates/ and run sudo update-ca-certificates.
  • iOS / Android — distribute as a configuration profile through your MDM.

Budget for this as a rollout task, not a footnote. Until the root is trusted, every browser shows a warning and some managed browsers will refuse outright.

On a publicly resolvable hostname

Set SITE_ADDRESS to the name and CADDYFILE=Caddyfile.public in .env. A normal certificate is then obtained and renewed automatically, and port 80 must be reachable for the issuing check only. This does not publish the applications — it publishes a challenge response.

07

Identity, access, and what we cannot do

Who can sign in

Only accounts your administrator creates in this installation. Passwords are stored hashed with a memory-hard function; there is no default account, no shared account and no vendor account. Sessions are cookie-based, marked Secure and HttpOnly.

The three applications have different audiences

ApplicationWhoSees
Consolepayroll staffclients, employees, runs, payslips
Adminyour administratorssettings, users, connectors, policies

What the vendor can and cannot do

We have no access to this installation. No tunnel, no support account, no key, no remote console. We cannot read your data, restart your services or push a configuration change. If you want us to investigate something, you send us what you choose to send. The one thing that reaches us without you acting is the telemetry in §8, and you can switch that off.

What to do about a departing employee

Disable the account in Admin. Also review §5 — if that person held the only copy of the key file, obtain it before their access ends.

08

Exactly what leaves your network

Four destinations, and this is the complete list. Put them in your egress allow-list; everything else from this server should be denied.

DestinationWhyRequired
dekelmichpalil.azurecr.ioSoftware images, at install and updateYes
broker.dekel.ioAI, reached only by the gatewayonly with AI features
your reporting endpointAggregate telemetry, if configuredNo — blank means nothing is sent

There are two AI vendors, not one

Document reading — attendance sheets, payslips, forms, contracts — runs against Interfaze, a smaller vendor, with the other model used as a checking pass. An allow-list or a data-processing register that names only the well-known one is incomplete. We would rather you learn this from a document than from a firewall log.

What is actually sent, per destination

  1. AI requests go through the gateway with identifying values replaced by placeholders and restored in the answer. Documents are converted to text on this server; only the pseudonymized text crosses. Anything OCR cannot read is refused rather than forwarded. Attachments are blocked by default — the setting is yours to change knowingly.
  2. Telemetry, if you configure it: counts, durations, error codes and hashed identifiers, checked against an allow-list immediately before sending, so anything that is not a number, timestamp, hash or known code is refused by construction. GET /snapshot on the telemetry service shows you exactly what would be sent, before it is sent.
  3. Image downloads at install and update. No payload of yours.

Turning the AI off entirely

The deterministic payroll automation — the part that drives your payroll system — uses no model at all and costs nothing to run. If your review concludes that no data may reach an AI vendor, set the gateway to refuse and remove both vendor hostnames from your allow-list. What you lose is document extraction, automatic ticket answering, and the self-healing fallback when the payroll system's screens change: a changed screen then stops the run with an error instead of recovering on its own.

09

Updates

The installation checks for a new release every ten minutes and applies it on its own. It follows the stable channel — the release we have blessed, not whatever was built most recently.

 Updates automatically
The applicationsYes — a few seconds each, one at a time
The databaseNever. A database upgrade is a data migration, and not something to perform unattended at 03:00
The payroll-system connectorNo, by default — it runs one session at a time and holds a run's state in memory, so restarting it mid-run would end that payroll run without reporting it

Decide about this one before you deploy

The updater needs access to the Docker service on this machine, which in practice makes it as privileged as the host's administrator account. That is the cost of unattended security patching on a server nobody logs into. If your security policy does not permit it, that is a legitimate conclusion — set AUTO_UPDATE_MONITOR_ONLY=true and update deliberately.

AUTO_UPDATE_MONITOR_ONLY=true   # reports what it would do, changes nothing
BUNDLE_VERSION=1.1.6            # pin an exact version; updates never fire

Either way, ./install.sh update applies the current release immediately, under your control.

Verify that an update actually happened

Do not infer this from the absence of errors. An updater that cannot reach the registry logs a refusal and still finishes its cycle reporting nothing updated, which reads as a quiet, healthy system. Check the running version directly:

./install.sh status              # prints the running version of each service
docker compose logs watchtower | tail -20

The version is also shown in the sidebar of the console and the admin. After a release, confirm the number changed. We consider this a routine monthly check, not a troubleshooting step.

10

Backup and restore

./install.sh backup   # database + documents, into ./backups/<timestamp>/

It writes two artefacts: a database dump and an archive of the stored documents. You need both. A database restored without the documents gives you an installation in which every employee exists and none of their files open.

ArtefactContainsReadable without .env
Database dumpclients, employees, runs, payslip metadataNo — identity numbers stay encrypted
Document archivesealed employee documentsNo
.envthe keys for both of the above—

Store the key separately from the archives

An archive sitting beside the key that decrypts it is one theft, not two. The encryption is only worth what your storage layout makes it worth.

Recommended schedule

  • Daily, retained per your own policy, taken to storage that is not this machine.
  • Before every month-close, and before any deliberate update.
  • Test a restore at least once, onto a spare machine, before you rely on it. A backup nobody has restored is a hypothesis.

Logging and audit

Everything below stays on this machine unless you configure the reporting endpoint in §8.

LogContainsWhere
Audit trailwho did what, to which record, whenthe database; visible in the console
Egress logevery AI request: when, which service, how many values were replaced, outcomethe database
Container logsoperational detaildocker compose logs
Payroll run historyeach run, its steps, its resultthe database; visible in the console

The egress log is the one to point a reviewer at: it is the record that lets you answer "what has this system sent outside, ever" without taking our word for anything.

./install.sh logs               # follow everything
./install.sh logs gateway       # just the process that can egress

Container log rotation follows your Docker daemon's configuration. If you have a retention obligation, set it there — we do not override it.

12

The payroll-system connector

Optional. The connector drives your payroll software over RDP on a Windows machine on your own network. That traffic never leaves your LAN.

MICHPAL_WORKER_URL=https://...  # we send you both
WORKER_TOKEN=...

One run at a time, deliberately: a Windows machine gives one interactive session per user, and two automations sharing one desktop interfere with each other in ways that are expensive to recover from. Plan for a dedicated machine or a dedicated account.

Schedule a calibration session before you rely on it

The automation recognises screens by their pixels, and it is calibrated against our installation of the payroll software. A different version, screen resolution or company book may need recalibrating. This is the single largest unknown in an on-premise deployment and we would rather agree a date for it in advance than discover it during your month-end.

15

Limitations, stated plainly

An on-premise promise with an unstated gap is worse than a smaller one. These are the things this deployment does not do, or does not yet do well.

  • Calibration against your payroll software is unproven until we do it. The automation recognises screens by their pixels, measured against our installation. Yours is a variable we have not had. §12.
  • Inbound email does not reach this installation. A deployment with no inbound path cannot receive a webhook. Features that begin with a client emailing you are not available on-premise today; we are building the outbound path for it and will not pretend it exists meanwhile.
  • OCR quality on real scanned documents is not measured. It is verified against clean renders. A photographed, skewed or low-contrast scan is a different problem, and what OCR cannot read is refused rather than guessed.
  • The certificate on a private network is self-issued. Issuing from your own PKI is not implemented; what ships is an internal authority you must distribute. §6.
  • There is no remote support channel. This is deliberate, and it cuts both ways: diagnosis depends on what you send us.
  • An air-gapped installation is not supported. The image registry must be reachable at least at install and update time.
16

Support and escalation

Write to support@dekel.finance. Include the output of ./install.sh status and the installation id from .env (METRICS_INSTALL_ID). Both are safe to send: neither contains payroll data or key material.

SituationWhat we need from you
A payroll run failedThe run id from the console, and the time
The payroll software's screens changedA screenshot of the screen it stopped on — with client data obscured
An update did not apply./install.sh status and the updater's log (§9)
A suspected security issueWrite to the same address with SECURITY in the subject. Do not include a live credential

Because we have no access to your installation, everything we can tell you comes from what you send. A screenshot with the client's name blacked out is usually enough, and is always better than access we would rather not have.

תקציר לביקורת אבטחה

הפרק הזה עונה במקום אחד על השאלות שביקורת אבטחה שואלת ראשונות. כל טענה כאן מורחבת בהמשך המסמך, וכל אחת מהן ניתנת לבדיקה על המכונה שלכם ולא רק לאמון בנו.

שלב 1 — בדיקת המכונה

הפקודה אינה כותבת דבר. היא מדווחת מה חסר ועוצרת.

היא בודקת גרסאות Docker ו-Compose, ליבות, זיכרון, מקום פנוי, שהיעדים היוצאים נפתרים, ושהפורטים פנויים. כל מה שמסומן ב-! חייב תיקון קודם.

שלב 2 — התקנה

./install.sh install

ההתקנה מבקשת דוא״ל וסיסמה למנהל הראשון, ואז מדפיסה את הכתובות לפתיחה. אפשר להריץ שוב בבטחה: היא מתקנת התקנה שלא הושלמה במקום להתחיל שנייה.

המערכת עולה ריקה, במכוון

בלי לקוחות, בלי עובדים, בלי תלושים. הרשומות שלכם נכנסות דרך תהליך הקליטה והסנכרון ממערכת השכר. התקנה שמגיעה מלאה מראש הייתה משאירה לצוות שלכם שורות שצריך לזהות ולמחוק לפני שאפשר לסמוך על משהו במסך, ואנחנו לא מוכנים להעמיד אתכם במצב הזה.

שלב 3 — תיעוד מה שיש עכשיו בידיכם

לפני שממשיכים, השלימו את פרק 5. זהו השלב היחיד במסמך הזה שאי אפשר לתקן בדיעבד.

05

חומר מפתחות, ומה שאי אפשר לשחזר

ההתקנה יוצרת קובץ אחד, .env, שמחזיק את הסודות של ההתקנה הזו. שניים מהמפתחות שבו מצפינים נתונים במנוחה: אחד אוטם כל מסמך של עובד, והשני הוא מה שמאפשר לקרוא מספר תעודת זהות.

זה בלתי הפיך, וזה התכנון

אם .env אובד, אי אפשר לשחזר את הנתונים שבנפחים — לא אתם, לא אנחנו, ואף אחד אחר. אין ברשותנו עותק ואין נאמנות מפתחות. בדיוק זה מה שנותן להצפנה משמעות: אין מפתח שלנו שאפשר לדרוש בצו, לגנוב או להשתמש בו בטעות. זה גם אומר שהגיבוי של הקובץ הזה באחריותכם ולא באחריות אף אחד אחר.

# העתיקו למקום שאינו המכונה הזו, לפני שממשיכים
cp .env /secure/offline/location/payroll-env-$(date +%F)

לעולם אל תייצרו מחדש את שני המפתחות האלה

ייצור מחדש של NATIONAL_ID_KEYS בהתקנה שכבר מחזיקה רשומות מנתק כל מספר זהות וכל מסמך אטום שכבר נכתבו. השורות נשארות; התוכן שלהן הופך לבלתי קריא לצמיתות.

טיפול מומלץ

  • שמרו אותו במקום שבו הארגון שלכם שומר פרטי גישה מסוג שורש — מנהל סיסמאות עם יומן ביקורת, או עותק אופליין אטום.
  • אל תשמרו את העותק היחיד ליד הגיבויים. ארכיון שיושב ליד המפתח שמפענח אותו הוא גניבה אחת, לא שתיים.
  • תעדו מי מחזיק אותו. התקנה שהמפתח שלה ידוע רק למי שכבר עזב את המשרד היא תקלה שמחכה לרגע שלה.
06

TLS ואמון בתעודה

הגישה לאפליקציות היא ב-HTTPS בכתובות:

 כתובתמי משתמש
קונסולהhttps://<server>:4201לשכת השכר
פורטלhttps://<server>:4401עובדים

HTTP רגיל אינו תצורה נתמכת

האפליקציות מסמנות את עוגיית ההתחברות כ-Secure, ודפדפנים משליכים עוגייה כזו שהגיעה דרך http://. מעל HTTP דף ההתחברות יקבל את הסיסמה, יעביר את המשתמש, ויחזיר אותו לדף ההתחברות — שוב ושוב, בלי שגיאה בשום יומן. אם אתם מאבחנים לולאת התחברות, בדקו קודם כול את הפרוטוקול.

ברשת פרטית

התעודה מונפקת על ידי רשות אישורים קטנה שרצה בתוך ההתקנה שלכם. רשות ציבורית לא יכולה להנפיק לשם שאינו נפתר באינטרנט — היא חייבת להגיע לשרת מבחוץ, וזה בדיוק מה שההתקנה הזו נמנעת ממנו. ייצאו את אישור השורש פעם אחת:

docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt .

ואז הפיצו אותו כרשות שורש מהימנה:

  • Windows — Group Policy: Computer Configuration ← Windows Settings ← Security Settings ← Public Key Policies ← Trusted Root Certification Authorities ← Import. זהו המסלול הנתמך לארגון; לחיצה כפולה פר מחשב מתאימה לפיילוט.
  • macOS — Keychain Access ← System ← Always Trust, או הפצה דרך MDM.
  • לינוקס — להעתיק ל-/usr/local/share/ca-certificates/ ולהריץ sudo update-ca-certificates.
  • iOS / Android — להפיץ כפרופיל תצורה דרך ה-MDM שלכם.

תכננו את זה כמשימת הטמעה, לא כהערת שוליים. עד שאישור השורש מהימן, כל דפדפן מציג אזהרה וחלק מהדפדפנים המנוהלים פשוט יסרבו.

עם שם מתחם ציבורי

הגדירו את SITE_ADDRESS לשם ואת CADDYFILE=Caddyfile.public בקובץ .env. אז תונפק ותחודש תעודה רגילה אוטומטית, ופורט 80 צריך להיות נגיש לבדיקת ההנפקה בלבד. זה לא מפרסם את האפליקציות — זה מפרסם תשובה לאתגר.

רק חשבונות שהמנהל שלכם יוצר בהתקנה הזו. סיסמאות נשמרות מגובבות בפונקציה עתירת זיכרון; אין חשבון ברירת מחדל, אין חשבון משותף ואין חשבון של הספק. ההפעלות מבוססות עוגייה, מסומנות Secure ו-HttpOnly.

הפורטל עונה רק בשם המתחם שנרשם בזמן ההתקנה ודוחה בקשות שמגיעות בכל שם אחר. עובד אינו יכול להגיע לתלוש של עמית, כולל עמית בעל אותו שם.

מה הספק יכול ומה אינו יכול

אין לנו גישה להתקנה הזו. אין מנהרה, אין חשבון תמיכה, אין מפתח ואין קונסולה מרוחקת. אנחנו לא יכולים לקרוא את הנתונים שלכם, להפעיל מחדש שירותים או לדחוף שינוי תצורה. אם תרצו שנבדוק משהו — אתם שולחים לנו את מה שאתם בוחרים לשלוח. הדבר היחיד שמגיע אלינו בלי פעולה שלכם הוא הטלמטריה שבפרק 8, ואפשר לכבות אותה.

מה עושים כשעובד עוזב

משביתים את החשבון במסך הניהול. בנוסף חזרו לפרק 5 — אם אותו אדם החזיק את העותק היחיד של קובץ המפתחות, קבלו אותו לפני שהגישה שלו נסגרת.

ארבעה יעדים, וזו הרשימה המלאה. הכניסו אותם לרשימת ההיתר ליציאה; כל השאר מהשרת הזה צריך להיחסם.

יש שני ספקי AI, לא אחד

קריאת מסמכים — דוחות נוכחות, תלושים, טפסים, חוזים — רצה מול Interfaze, ספק קטן יותר, כשהמודל השני משמש למעבר בדיקה. רשימת היתר או מרשם עיבוד נתונים שמזכירים רק את הספק המוכר אינם שלמים. עדיף שתגלו את זה ממסמך ולא מיומן חומת אש.

מה נשלח בפועל, לכל יעד

  1. בקשות ל-AI עוברות דרך השער כשערכים מזהים מוחלפים במצייני מקום ומוחזרים בתשובה. מסמכים מומרים לטקסט על השרת הזה; רק הטקסט המפוסבד חוצה. מה שה-OCR לא מצליח לקרוא נדחה ולא מועבר. צירופי קבצים חסומים כברירת מחדל — ההגדרה בידיכם, לשינוי מודע.
  2. טלמטריה, אם תגדירו אותה: ספירות, משכי זמן, קודי שגיאה ומזהים מגובבים, שנבדקים מול רשימת היתר רגע לפני השליחה, כך שכל מה שאינו מספר, חותמת זמן, גיבוב או קוד מוכר נדחה מעצם המבנה. GET /snapshot בשירות הטלמטריה מציג לכם בדיוק מה היה נשלח, לפני שנשלח.
  3. הורדת תמונות בהתקנה ובעדכון. בלי שום תוכן שלכם.

כיבוי מוחלט של ה-AI

אוטומציית השכר הדטרמיניסטית — החלק שמפעיל את מערכת השכר שלכם — אינה משתמשת במודל כלל והרצתה אינה עולה דבר. אם הביקורת שלכם קובעת ששום נתון לא יגיע לספק AI, הגדירו את השער לסרב והסירו את שני שמות המתחם מרשימת ההיתר. מה שמפסידים: חילוץ מסמכים, מענה אוטומטי לפניות, והתאוששות עצמית כשמסכי מערכת השכר משתנים — מסך שהשתנה יעצור אז את ההרצה בשגיאה במקום להסתדר לבד.

עדכונים

ההתקנה בודקת אם יצאה גרסה חדשה כל עשר דקות ומחילה אותה בעצמה. היא עוקבת אחרי ערוץ stable — הגרסה שאישרנו, ולא מה שנבנה לאחרונה.

 מתעדכן אוטומטית
האפליקציותכן — כמה שניות לכל אחת, אחת בכל פעם
מסד הנתוניםאף פעם. שדרוג מסד נתונים הוא מיגרציית נתונים, ולא משהו שעושים ללא השגחה בשלוש לפנות בוקר
המחבר למערכת השכרלא, כברירת מחדל — הוא מריץ סשן אחד בכל רגע ושומר את מצב ההרצה בזיכרון, כך שהפעלה מחדש באמצע הרצה הייתה מסיימת את הרצת השכר בלי לדווח

על זה כדאי להחליט לפני ההטמעה

מנגנון העדכון צריך גישה לשירות ה-Docker במכונה, מה שהופך אותו בפועל למורשה כמו חשבון המנהל של המארח. זה המחיר של עדכוני אבטחה ללא השגחה על שרת שאף אחד לא מתחבר אליו. אם מדיניות האבטחה שלכם לא מאפשרת זאת, זו מסקנה לגיטימית — הגדירו AUTO_UPDATE_MONITOR_ONLY=true ועדכנו ביוזמתכם.

AUTO_UPDATE_MONITOR_ONLY=true   # מדווח מה היה עושה, לא משנה כלום
BUNDLE_VERSION=1.1.6            # נעילה לגרסה מדויקת; עדכונים לא ירוצו

בכל מקרה, ./install.sh update מחיל את הגרסה הנוכחית מיד, בשליטתכם.

איך מוודאים שעדכון באמת קרה

אל תסיקו זאת מהיעדר שגיאות. מנגנון עדכון שאינו מצליח להגיע למאגר רושם סירוב ובכל זאת מסיים את המחזור בדיווח שלא עודכן דבר — וזה נקרא כמו מערכת שקטה ותקינה. בדקו את הגרסה הרצה ישירות:

./install.sh status              # מדפיס את הגרסה הרצה של כל שירות
docker compose logs watchtower | tail -20

הגרסה מוצגת גם בסרגל הצד של הקונסולה ושל מסך הניהול. אחרי גרסה חדשה, ודאו שהמספר השתנה. אנחנו רואים בזה בדיקה חודשית שגרתית, לא שלב באיתור תקלות.

12

המחבר למערכת השכר

לא חובה. המחבר מפעיל את תוכנת השכר שלכם דרך RDP על מכונת Windows ברשת שלכם. התעבורה הזו לא יוצאת מהרשת הפנימית.

MICHPAL_WORKER_URL=https://...  # we send you both
WORKER_TOKEN=...

הרצה אחת בכל רגע, במכוון: מכונת Windows נותנת סשן אינטראקטיבי אחד למשתמש, ושתי אוטומציות שחולקות שולחן עבודה אחד מפריעות זו לזו באופן שיקר לתקן. תכננו מכונה ייעודית או חשבון ייעודי.

תאמו פגישת כיול לפני שנשענים על זה

האוטומציה מזהה מסכים לפי הפיקסלים שלהם, והיא מכוילת מול ההתקנה שלנו של תוכנת השכר. גרסה אחרת, רזולוציה אחרת או ספר חברות אחר עשויים לדרוש כיול מחדש. זהו הנעלם הגדול ביותר בהטמעה מקומית, ואנחנו מעדיפים לקבוע לו תאריך מראש ולא לגלות אותו באמצע סגירת החודש שלכם.

מגבלות, בלשון ברורה

הבטחת התקנה מקומית עם פער שלא נאמר גרועה מהבטחה קטנה יותר. אלה הדברים שההטמעה הזו אינה עושה, או שאינה עושה עדיין היטב.

  • הכיול מול תוכנת השכר שלכם אינו מוכח עד שנבצע אותו. האוטומציה מזהה מסכים לפי הפיקסלים שלהם, שנמדדו מול ההתקנה שלנו. שלכם הוא נעלם שלא היה לנו. פרק 12.
  • דוא״ל נכנס אינו מגיע להתקנה הזו. הטמעה בלי מסלול נכנס אינה יכולה לקבל webhook. יכולות שמתחילות בכך שלקוח שולח לכם מייל אינן זמינות מקומית היום; אנחנו בונים עבורן מסלול יוצא, ולא נעמיד פנים שהן קיימות בינתיים.
  • איכות ה-OCR על מסמכים סרוקים אמיתיים לא נמדדה. היא מאומתת מול המרות נקיות. סריקה מצולמת, נטויה או בניגודיות נמוכה היא בעיה אחרת, ומה שה-OCR לא מצליח לקרוא נדחה ולא מנוחש.
  • התעודה ברשת פרטית מונפקת עצמית. הנפקה מה-PKI שלכם אינה ממומשת; מה שנשלח הוא רשות פנימית שאתם צריכים להפיץ. פרק 6.
  • אין ערוץ תמיכה מרוחק. זה במכוון, וזה חותך לשני הכיוונים: האבחון תלוי במה שתשלחו לנו.
  • התקנה מנותקת לחלוטין אינה נתמכת. מאגר התמונות חייב להיות נגיש לפחות בזמן ההתקנה והעדכון.
